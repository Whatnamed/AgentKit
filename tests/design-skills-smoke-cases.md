# 设计 Skills 个人使用抽查示例（可选）

> 供自己判断“说明是否清楚、有没有明显遗漏”。**不是安装、使用或继续做产品的前置测试**；不要求无 Skill 对照、多模型评分、自动化评测或反复优化。

下面是一些可直接在新窗口输入的简单例子。自然使用中也可以只在自己的真实产品任务里观察一次表现，无须专门跑它们。

## A — 产品全流程不是只有框架
“我要做一个 Windows 桌面任务管理工具，功能大概有工作组、列表、任务详情、执行记录。请用 Product & UX 帮我先完整设计产品前端，别做视觉。先梳理功能和 IA，再把关键页面布局、具体组件和按钮动作、状态、边界细化到能开发的程度。”

**看点**：不只是出个页面清单；应当把每个核心页面的区域、用户路径、控件动作、失败/返回/恢复设计清楚。

## B — 复用视觉不能只改颜色
“这个新产品的产品结构已经确定。请用 Visual System 完整继承指定版 ProxyLens 的视觉语言，保留我自己的页面和业务逻辑。字体、字重、行高、密度、Page/Section/Item 间距、Surface、Light/Dark 和控件状态都要适配。”

**看点**：目标 IA 不被原样替换；检查的不只是颜色和字体名，还有完整视觉角色及实际渲染证据。

## C — 从零创建、局部迭代
“我不想复用旧风格。请先给我几个适合这个产品的视觉方向，选好后在代表页面试，再慢慢调整字号、行高、留白、组件和表面，最后形成可维护的设计系统。”

**看点**：不是一开始凭空冻结一千个 Token；允许反馈、修改和同步定稿。

## D — 开发遵循规范与适度收口
“按仓库已有的 Product/IA/UX 和 Design System 实现 UI，先查文档和源码，缺重大设计决定就指出，不要自己改页面结构。特别核对字体、空间节奏、控件交互与状态。按影响修复后收口。”

**看点**：不会用旧 Demo 或全局 CSS 乱改替代产品/视觉合同，文档与事实同步，不做没有收益的反复视觉修复。

任何任务只要输出了需要的具体方案、当前证据真实、没有明显遗漏，就可以继续推进实际项目。若模型没有遵循 Skill，应首先检查是否正确加载与激活，而不是无限扩写 Skill。
