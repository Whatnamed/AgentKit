# 按已确认设计开发和维护前端

## 定位

这是**开发执行纪律**，不是重新做产品设计的指令。适用于新建 UI、从参考系统移植视觉、局部交互修复、字体/空间迭代、真正的 UI 收口。按任务规模控制输出，不额外生成大量计划或实验工程。

## 开始实现前

1. **定位单一事实来源与职责**：阅读项目 `AGENTS.md`、当前产品/功能规格、IA、逐页 UX 交互、视觉系统、Token/组件参考以及当前实现/状态文档。区分**目标决定**与**真实代码现实**，识别历史文档和已否定方案。文档缺失时不要臆造“已定”，应标注可实现部分与需要产品决策的缺口。
2. **把设计映射到代码**：列清本轮受影响页面、区域、核心控件、动作/数据来源和状态，确保每个应存在的功能都有实际可操作的 UI；不要因已有通用组件或 Demo 页面架构而改变产品页面职责。
3. **遵守工作边界**：用户已确认的产品布局、交互、状态、视觉方向优先；重大冲突/缺失应报告给产品设计环节，并提出具体备选，不擅自用实现方便当设计授权。普通工程细节可由执行者合理决定，不需要为每个变量问用户。
4. **明确最小修改集**：局部 UI 修复先排除“规范不适用 / 实现偏离 / 环境差异 / 规范缺项”，必要时查实际渲染字体和组件状态；不要一次无依据地同时改多个视觉参数。可按需读 [工程纪律](references/ui-implementation-discipline.md)。

## 实现顺序

- 新产品：**共用 Token/字体/primitive → shell → 最能检验密度与状态的真实代表页面 → 其余逐页 → Light/Dark 与异常/窄屏**。产品自身组件可按职责组合，不套源系统业务页面。
- 页面和控件必须完成实际产品合同：列表、表单、过滤、选中与展开、确认/取消、异步 busy、错误、Empty、Unknown、跨页上下文、键盘/长内容等。根据项目数据事实实现，不能添加假按钮、假数据/假通过状态。
- 视觉系统迁移必须落到字体文件和实际渲染、字重、行高、间距级别、表面角色、状态及组件几何，不能只套颜色。全局 Token 和组件集中维护，局部业务例外需要注释/规格记录；避免重复/相互覆盖的 CSS。
- 组件、视觉状态和布局一次验证一组真实代表情况。若新视觉仍在探索期，临时调色实验或局部候选与生产规则隔离，定稿后清理，不让实验入口成为产品功能。
- 用不超出必要范围的 typecheck/lint/测试、真实浏览器或宿主验证受影响路径；涉及桌面 DPI/系统控件/字体问题，浏览器预览不能直接等同真实桌面验收。

## 交付与同步

- 代码落实**已有决定**后，更新对应的产品 IA/UX、设计系统/Token、组件参考和状态记录；不要重复造许多互相冲突的文档。稳定项目规则写 `AGENTS.md`，阶段进度写 STATUS/计划/开发日志，窗口交接属于另一种材料。
- 同步源文件、文档与实际证据等级：构建通过、自动测试、真实交互、运行时视觉、人工接受是不同概念。若缺测试设备/真实数据，标记 `deferred` 并提供最小复现步骤，不宣称整体验收。
- 报告要能让用户理解**界面实际会怎样变化**，避免只讲底层代码。提供变动范围、重要限制、如何自己核对，以及是否有真正阻塞项。
- 多轮局部修复后重新看受影响整个页面/流程，防止补丁叠加；按任务/回归/用户影响达到目标便停止，不额外硬化和无限视觉 polish。

## 特别避免的历史问题

避免将功能清单直接平铺成 Demo；把不同页面因代码复用套同一布局；标题后自动添加同义解释文字、空 KPI 卡；把错误/未知写成 0；字体 fallback 和大小行高相互抵消；“修对齐”同时打乱整个 spacing；只核对源码不看真实状态；声明冻结但文档/实现脱节；把未经确认的产品方案交给 Coding Agent 自行决策。

**完成条件**：当前范围内用户能按规格完成完整操作，视觉在必要真实场景中符合当前设计规则；代码、文档与剩余未验证事项一致。只在本轮明确要求的范围内收口。
