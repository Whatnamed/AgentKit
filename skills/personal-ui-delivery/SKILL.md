# Personal UI Delivery

## 任务定位

这是**执行已确定的产品与视觉设计**的个人协作 Skill，不替代产品定义、信息架构、视觉方向选择或架构决策。目标是让实现准确反映已有决定，并把旧项目里反复出现的 UI 问题尽可能在开发时处理掉。

适用于新建页面、改版、从其他产品迁移视觉系统、视觉微调与 UI 验收。只完成用户要求的范围：局部问题直接修，完整页面/跨模块工作再使用短任务计划；不要每次自动制作整套设计文档或执行大型审核。

## 1. 先找到事实和权威

开始前按**目标仓库自己的约定**读必要资料，通常包括：

1. 仓库级 `AGENTS.md` / `README` / `STATUS`，以及当前分支、工作树和实际代码；
2. 产品功能与领域语义、**信息架构 / 页面职责**、**逐页 UX 与交互状态**；
3. 视觉设计系统的入口、Typography、Tokens、组件/状态规范、来源版本和适用例外；
4. 与本任务直接相关的 API / 数据合同、禁区、安全限制、现有测试及运行方式。

不要臆测文件名固定存在；按仓库实际导航找。区分三种不同的事实：

- **已决定的目标**：产品/UX/视觉规范要实现什么，用户后来否定了什么；
- **当前实现**：代码与运行时实际做到了什么、哪些仍为旧 UI / Demo / 目标草案；
- **可信证据**：代码检查、构建、自动测试、真实运行、人工验收各能证明到哪一层。

当三者不一致时，先定位差异，判断是规格自身需要修改、实现偏离、环境/资源问题，还是规格缺项。**不能悄悄让旧代码、截图或源产品组件成为目标产品设计权威。**

## 2. 将规格落实为可操作的 UI

对本轮受影响页面或流程，内部核对“目标规格 → 真实代码 → 可操作行为”：

- **页面结构**：Page/Section/Group/Item/Metadata 的职责、顺序和主次；导航、侧栏、列表、详情、弹层、滚动与窄窗行为，与当前 IA 一致。
- **细节与小操作**：按钮、搜索/筛选/清空、选中与展开、导航返回、表单输入与取消、保存/撤销、危险操作、长文本/Tooltip、键盘与焦点；关键交互各有触发、反馈与结果。
- **状态真实性**：Loading、Empty、Error、Unknown、部分完成、权限/数据来源不可用、异步忙碌、重复点击、恢复与持久化，按当前项目的真实业务/接口能力实施。不能因示例或好看而编造成绩、活动、状态或可用动作。
- **跨页面与对象隔离**：用户更换对象、筛选、切页、关闭详情、重启后，哪些上下文需要保留或重置，应按 UX 合同做；不意外触发与当前操作无关的行为。
- **复用边界**：复用基础 Token、primitives 和确有相同职责的组件；**不为复用代码把不同页面强制做成同一种布局**。不要把静态设计参考直接变成整个产品的业务页面。

复杂任务可以用一张简短差异表定位缺口；小修复不必输出它。**重要产品/交互决定未被确认时，不自行做最终取舍**：先实施不依赖该决定的部分，并报告真正阻塞的选择。纯工程实现细节可自行解决，不要求用户逐项批准。

## 3. 视觉落地与问题诊断

视觉继承不能停在复制颜色、字体名或圆角。实现还需要符合目标系统的：

- 文字角色与**真实字体资源**、字重、fallback、中英混排、Mono/tabular 使用场景、字号、行高、字距和基线；
- Page/Section/Group/Item/Control 的留白层级、分组、内外间距、密度、对齐与内容优先级；
- Canvas、Sidebar、Workspace、Raised/Inset、Popover/Inspector 等适用表面层级；
- 控件几何、图标光学中心、边框、阴影、hover/selected/focus/disabled/busy、Light/Dark 及长文本/缩放行为。

遇到“不齐、太松、字体不对、层次不清”等问题，先看**当前设计规则 + 当前计算样式/渲染 + 实际资源**。检查 `@font-face`、文件打包、字形覆盖和运行宿主，不以 CSS family 声明认定真实字体；几何中心、文本 baseline 与视觉中心不是一回事。

按证据选择最小合理修改集，避免没有归因就同时改变字体、字重、行高、字距、padding 和全局间距。联动修改确有必要时应说明因果及受影响页面。全局值归单一 Token/组件权威，页面例外有理由地保留；避免一层层叠加覆盖 CSS 作为永久修复。

**产品布局职责已定，视觉移植不能重新发明导航或删减功能。** 若视觉改进确实影响核心 IA/行为，先让产品设计决策明确，而不是实现者直接改掉。

细节参见 [实现诊断与文档责任](references/ui-implementation-discipline.md)；仅相关时读取。

## 4. 修改、验证与交付

1. **按范围修改**：遵守目标仓库分支、冻结文件、隐私与禁止操作约束；不覆盖未提交修改，不附带改无关架构或数据语义。规模较大时先明确阶段与依赖，短启动 Prompt 引用已有详细计划即可。
2. **验证用户真正会做的事情**：先运行与改动匹配的 typecheck/lint/测试，再检查受影响页面或任务路径；UI 可渲染时看代表性内容和状态。涉及字体、系统控件、DPI/窗口缩放或桌面桥接，要区别浏览器预览与真实目标宿主；不要求每个小修复重复全部场景矩阵。
3. **对照整体效果**：多轮局部修补后回看本轮受影响页面/流程，避免解决某个对齐问题却造成跨语言、深色主题、列表密度或其他组件的回归。
4. **维护正确的文档**：若**产品/UX/视觉规则发生被批准的变化**，修改相应权威规格；若只是代码追上原规格，无须无意义重写产品文档，但应按项目约定更新必要的实现状态/日志。稳定协作规则才写 `AGENTS.md`，不要将阶段进度、一次性 Prompt 或网页窗口交接塞进去。
5. **准确报告证据**：简明说明用户看得见的改动、代码/文档触及范围、已执行检查、真实验证结果及未解决依赖。构建通过 ≠ 交互已验证 ≠ 桌面视觉已验收；条件不足时记 `deferred / not-verified`，不报虚假的 PASS。

## 5. 收口标准

范围内的必要页面/控件行为与**已确认**产品、UX、视觉规则一致；受影响的用户任务可以走通，异常与关键状态不误导；本轮有足够的实际证据，无法验证的部分已明确记录，即可结束。

**不要为找问题而找问题**，也不要在用户没有授权时自动开始新阶段、扩大修复范围或发起大规模视觉 polish。能清楚说明还缺什么现实条件，比重复尝试并虚报“全部完成”更好。
