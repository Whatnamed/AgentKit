# 前端实现中的设计一致性与文档责任

## 开工前 6 个问题

1. 当前目标产品规格和 IA/UX 哪些已经决定？它们位于何处、什么版本？
2. 当前 UI 代码已经做到了哪儿？是不是旧 Demo 或实验分支，是否与目标矛盾？
3. 视觉系统是否已选、是从零创建还是完整继承？有哪些源 commit、Token、字体和组件状态？
4. 本轮改动会影响哪些页面、组件、状态、主题、宽度与语言？
5. 如果实际效果不正确，是规范本身有问题、实现错了、数据事实不同还是渲染环境造成？
6. 当前任务到什么程度就可结束？哪些属于受阻前置条件，而不是尚未完成的功能？

## 常见陷阱 → 预防

- **不查文档就改 CSS** → 先定目标规则与问题根因，然后改最小影响集。
- **为了代码复用统一业务 UI** → 共用 primitive/Token，不强行共用页面结构；测试工作台和题库目录的职责本来可能不同。
- **硬编码视觉值** → 优先语义 Token/组件变体；确有业务专属例外时记在设计规范。
- **一处字体难看就全局放大行高** → 核对 `@font-face`、打包、fallback、渲染字体与真实控件尺寸，逐项比较。
- **按钮存在但没有真实行为** → 检查是否具备数据/接口；不存在就真实禁用或标未实现，不能装成可用。
- **默认每级加副标题或更多彩色卡片** → 文案只在说明新事实或下一步时存在；区域边界与空间因任务而定。
- **原生控件与系统不一致** → 针对平台检查所有实际出现的输入/选择/日期/对话框的状态与主题；不意味着所有控件必须自绘。
- **只跑 build 就宣布验收** → 涉及可见 UI 的任务要看真实显示和受影响动作，失败时写明缺少的环境/证据。
- **已确认方案被实现者悄悄改了** → 记录差异和原因，让产品/设计方决定；不要让当前代码覆盖目标规范。
- **每次复审无限升级任务** → 按重要性、明确边界和停止条件收口，避免反复微调无收益。

## 文档责任

| 文件类别 | 负责什么 | 不应放什么 |
| --- | --- | --- |
| `AGENTS.md` | 本项目长期协作规则、稳定限制、入口路径 | 每日开发进度、当前 HEAD、窗口交接 |
| Product/IA/UX | 功能、信息架构、状态和交互的目标决策 | 运行测试流水账、配色 token |
| Design System | 主题、Typography、空间规则、组件/视觉状态及源映射 | 尚未确认的业务页面职责 |
| STATUS/Plan/Devlog | 实现现实、阶段范围、测试、未完成、后续依赖 | 与长期规范冲突的第二份产品设计 |
| 原始聊天/Handoff | 历史原因和会话连续性 | 直接冒充当前代码/正式设计权威 |

审查时先报告“哪些被实施、哪些未实施、哪些因真实依赖被延期”。同一次任务不强制创建所有文档类别。
