# UI 实现诊断与文档责任

> 这是 `personal-ui-delivery` 的**按需参考**：只有遇到多文档冲突、视觉反复漂移或需要交付复核时阅读。不必每轮把检查表全部抄进工作日志。

## 1. 三种权威别混在一起

| 需要回答什么 | 应从哪里找 | 不能拿什么替代 |
| --- | --- | --- |
| 产品应该做什么 | 已确认 Product/功能、IA/逐页 UX、真实状态语义 | 当前旧 Demo、某张参考图、Agent 自己的猜测 |
| 应该长什么样 | 指定版本的 Design System、Typography、Tokens、组件/视觉状态与例外 | 单个截图或另一个产品的业务页面 |
| 现在实际上有什么 | 当前分支真实代码、API、数据、运行效果、测试/日志与 STATUS | 理想规格、旧执行报告、“已有这个按钮” |
| 哪些已验收 | 与本轮环境/状态对应的真实证据 | build pass、CSS 声明、其它项目的验收结果 |

遇到冲突先指出“目标 vs 当前实现”具体差异，决定要修改代码还是需要产品/设计方修订目标规格。**目标规格不能自动声称已实现；当前代码也不能自动反过来定义目标。**

## 2. 反复遇到的问题与正确定位

| 现象 | 先核对 | 应避免 |
| --- | --- | --- |
| 页面像 Demo，功能平铺 | 用户任务、IA、真实页面 Section 与动作路径是否已定 | 为显得完整硬加首页、同义副标题、无意义 KPI、彩色卡片与空状态 |
| 不同任务页面被做成同一种布局 | 页面职责、目录 vs 原位工作、持续详情 vs 临时 Inspector | 以视觉继承或代码复用替代目标产品 IA |
| 选中、展开、切页点击相互误触发 | 每个 affordance 的独立动作、焦点、事件冒泡与状态 | 整条可点又把子操作当作同一动作 |
| 中文排版、行高、按钮对齐漂移 | 字体文件实际加载、CJK fallback、font weight、computed styles、DPI、文字基线、图标 viewBox | 为某种语言硬写负 margin/translateY，然后再扩大行高补偿 |
| 视觉层次不清、留白不一致 | Page/Section/Item/Metadata 的分组、行高和间距节奏，Surface 与 border 角色 | 同时全局增大 padding/gap/font-size，或给所有模块加卡片 |
| hover/selected/focus 与状态颜色冲突 | 交互状态和数据语义是否分离；Light/Dark、badge/legend 的可辨性 | 只靠一种颜色表达所有信息，或用装饰色掩盖含义 |
| 某页字体、控件不符合视觉系统 | 源系统与目标技术栈的实际字体、资产许可、原生控件、Token/组件映射 | 只复制 CSS 变量名，未验证真实宿主 |
| UI 有按钮但没有能力 | 当前 API/Controller、用户身份/任务状态、允许的操作与错误反馈 | 假启动、假评分、假进度、空操作，或混淆 unknown 与 zero |
| 修了几个小点反而别处变坏 | 组件共用范围、CSS 优先级和覆盖链、最近一轮全部变动 | 无根因继续多层覆盖 CSS，或只看修复位置 |
| 审查反复不结束 | 当前任务真正的 blocking 缺陷与用户影响、剩余依赖 | 每轮找一堆低风险主观问题，扩大原定范围 |

这些是**问题识别方法**，不代表所有新产品必须出现相同导航、相同视觉风格或字段。

## 3. 运行验证要与修改成比例

**局部改动**：对目标组件、有关联的使用处和必要状态做简短检查即可；不用每次运行大规模视觉回归。

**页面改造**：完整走通该页的主操作路径、进入/离开、空/多数据、常见失败、长文本与焦点；适用时检查主题和窄窗。

**跨页或完整新 UI**：沿产品权威规格验证端到端任务、上下文/持久化及数据正确性；根据目标技术实际覆盖浏览器或 Windows 宿主、窗口缩放、真实字体与系统交互。旧产品已有验收并不证明新产品已通过。

若环境/外部能力缺失，提供真实可执行的人工复验步骤和 `deferred` 理由。不要为了拿到 PASS 改验收标准、伪造数据或解除原项目安全停线。

## 4. 文档放对地方

| 文件职责 | 维护时机 | 不应做什么 |
| --- | --- | --- |
| `AGENTS.md`（长期规则） | 稳定协作/安全规范确实变化 | 写最新 HEAD、开发进度、一次性 Prompt |
| Product/IA/UX | 用户批准的功能、页面责任、交互/状态目标变化 | 把实现日志混进产品规则；代码一更新就全文重写 |
| Design System | 被采纳的 Token、Typography、空间节奏、组件/状态规则变化 | 让文档长期声明已冻结而实际 UI 已偏离 |
| Architecture / API / Domain | 确认的实现边界与接口/对象合同变化 | 让 UI 隐含改变领域事实 |
| STATUS / Devlog / Plan | 当前已实现、证据、阻塞与下一阶段 | 复写全部权威规范、用户网页窗口交接 |
| Prompt / Handoff | 本轮执行说明、会话连续性 | 当成长期规格或自动提交到仓库 |

不能假定所有仓库都采用同样文件名；首先确认目标仓库真实约定。小任务不强制新增文件；大任务有独立 Plan 时，启动 Prompt 保持简短并引用它。

## 5. 不在电脑旁或无需交互的情况

只有用户明确要求“无需提问、自主执行”时：

- 先执行已明确、低风险且不依赖重大未定设计决定的任务；
- 记录确实无法自行解决的产品/架构/安全选择，暂停**受影响部分**，继续完成其余安全独立部分；
- 不因“不要提问”擅自扩大授权、修改冻结验收、安全规则或删除重要资料；
- 完成后说明已经做成什么、哪些是未决/延期，不把部分完成伪装成全部完成。

## 6. 一个贴近真实工作的最短使用法

在 Coding Agent 的执行指令里引用该 Skill 的真实路径，并告诉它：

“先按照 `personal-ui-delivery` 核对本项目 `AGENTS.md`、当前状态、Product/IA/UX、Design System 和相关源码。以已确认的产品/视觉决策为目标，不把旧 Demo 当权威；实现受影响页面的具体交互与视觉细节，相关问题查根因再小范围修改。验证实际关键路径，更新需要维护的文档，按证据汇报并收口。其他业务/安全规则以目标仓库为准。”

目标项目里有什么页面、选了哪套视觉、当前 API 能做到什么，应该由**目标仓库**决定，而不是通用 Skill 写死。
