# Repro-first Debug

## 什么时候用

用户明确希望**诊断具体故障**，特别是偶发问题、性能退化、跨层数据状态错乱、改了几次仍未解决，或风险不适合继续猜测时使用。

**明显且低风险的小错误**（拼写、明确可定位的参数/语法错误、一次性修正）可以直接定位并修复，用最窄验证结束；不自动升级成六阶段大型 Debug 项目。性能**优化探索**（没有已知退化或失败症状）不是本 Skill 的同一种任务。

## 操作

1. **锁定症状和正确行为**：区分用户实际看到的现象与此前 Agent 的解释。明确时间、输入/状态、真实环境、发生概率、预期与实际、何时从正常变成异常。先读现有项目约定、相关源码/日志与近期 diff，不靠代码“看着可疑”先猜根因。
2. **得到足够可靠的失败证据**：已有准确错误/堆栈/可重复步骤足够时不要再建 harness；复杂情况选择能真正触发**同一个症状**的最便宜方法：现有针对性测试、CLI/API 请求、局部 UI 操作、捕获日志或必要的最小脚本。优先短且可重复，无法复现时如实记录证据、概率和限制，避免凭空生成模拟数据后把模拟通过当故障已解决。按需读 [复现和假设工具箱](references/repro-and-root-cause.md)。
3. **定位因果链**：跟踪失败进入哪一层、真实数据与状态如何流动，对照最近变更/正常路径；形成可以被证伪的假设，按影响和现有证据排序。根据可用条件使用断点、少量带标记日志、差分/二分、性能基线。**先证明或排除关键假设，再改生产代码**。
4. **有界修复**：针对已支持的根因做最小改动，复用项目已有错误处理/恢复约定；避免顺手重构、增加无必要的 fallback/retry/cache/备份、额外状态层和抽象。若需设计/领域合同变更，应先说明真实冲突，不由 Debugger 擅定重要产品规则。
5. **最小有效验证**：重跑原故障路径，检查修复是否改变症状，且未破坏直接相邻的工作路径。值得长期防回归、且存在真实测试切入点时再留下针对性回归测试；没有合适 seam 时不写不能捕获该 Bug 的虚假测试。小修复可由现有测试或真实操作验证；高风险变化按项目要求扩展验证范围。
6. **清理与收口**：删除自己添加的临时 instrumentation/一次性实验文件，保留用户原有工作和必要的测试；写清已证实的根因、改动、复现前后、未覆盖环境和继续调查条件。无需为每个 Bug 新增诊断手册。

## 失败与停线

- 一次针对性修改失败：先撤回假设或复核证据，**不要在错误前提上继续堆补丁**。
- 多次有证据的修复仍反复失败、明显涉及深层架构/外部系统时：停止扩大改动，说明哪条证据或设计决定需要解决，保留已安全完成的部分。
- 依赖真实桌面、特定设备、用户账户或第三方系统而当前环境无法验证时：输出最短人工复现/验收方式，状态记 `not verified`，不是通过。
- 不主动做额外快照、分支或备份；以现有 Git 历史和用户明确的保存/恢复约定为先。涉及不可逆数据或生产环境操作时遵守真实项目安全规则。

## 交付

简洁说明“**症状 → 复现证据 → 根因（确认/假设）→ 修正 → 原症状验证 → 剩余不确定性**”。不需要逐步仪式化汇报所有尝试；没有找到根因就不宣称已解决，也不为证明努力而写大批没有价值的测试。
