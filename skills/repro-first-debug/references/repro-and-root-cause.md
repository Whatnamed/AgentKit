# 适度复现、根因调查与性能诊断工具箱

按难度选一种或少数几种，**不是规定全做**。来源：[Matt Pocock diagnosing-bugs](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/diagnosing-bugs/SKILL.md) 与 [Superpowers systematic-debugging](https://github.com/obra/superpowers/blob/bb92a77741419a4ab5f06e711a283343f1ada0c3/skills/systematic-debugging/SKILL.md)；我们刻意没有继承“所有 Bug 必须写失败测试”的硬门禁。

| 症状类型 | 优先的低成本证据 | 必要时升级 |
| --- | --- | --- |
| 明确编译或语法错误 | 错误行/堆栈、对应调用点，单次复编译 | 相关调用路径、工具链/SDK 版本 |
| 单个可复现操作 | 现有单项测试、API/CLI 调用、实际 UI 路径 | 局部脚本捕获数据/状态，适用时最小集成测试 |
| 难复现偶发竞态 | 事件时间线、并发/重入关键路径、已有日志 | 多次重复触发、固定随机种子、针对性 tracing |
| 跨层输入或状态错误 | 入口→服务→持久化→呈现，逐边界记录有无真实数据 | 对照正常链路，在失效边界设置断点/标记日志 |
| 某版本之后退化 | 前后两个已知工作状态的 diff、环境/依赖变动 | 对照运行、局部 `git bisect` |
| 性能退化/卡顿 | 同一环境可比较的 FPS/延迟/CPU/内存基线和场景 | profiler、查询计划、热点定位，避免先“优化” |
| 只有用户机器上出问题 | 用户可描述的最短步骤、设备/系统/版本差异 | 在不泄露隐私的前提下收集相关日志或由用户做一轮手动检查 |

## 避免无效反馈回路

- 测试必须能**识别原始故障**：仅验证函数调用成功、没有异常，不等于复现了偶发状态错乱或用户 UI 问题。
- 自动化 harness 的搭建/维护成本如果高于当前问题，应优先利用现有程序、命令或用户手动一次复现。
- 严格一因一果：每次只改变足以验证假设的因素；不要 5 个猜测同时修改后看结果。
- 临时日志有标记，成功后清理；日志、HAR、截图、trace 必须按项目隐私规则脱敏。
- 如果主要证据来自已知运行环境，而不是当前可运行环境，说明“原因疑似/范围未验证”，不制造虚假成功证明。
- 可复现但当前无法可靠解决：如实说明最可能问题位置与还需要什么证据，不强行新增防御分支来遮掩根因。

## 结束标准

重现或准确捕捉过的真实症状在修复后不再出现（或经过合理范围重复检查），影响到的邻接路径无已知回归，临时仪器已经清理，未验证情况被清楚标记，即可结束。**不是测试越多、迭代越久越好**。
