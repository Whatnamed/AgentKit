# 产品定义与需求整理

## 目标

把用户已有的想法变成**足以继续做完整产品 IA/交互设计**的具体输入，而不是一份空泛商业计划或漂亮 PRD。尊重用户已经确定的功能、约束、排除项和选择；从真实项目、竞品和经验补足**关键遗漏**，但以候选建议呈现，不能假装用户已经确认。

## 从什么开始

- 先看当前输入、已有文档、仓库真实能力与此前明确决定；区分已确定、提议、需要查证和已否定的方案。正在改版时不能直接沿用旧产品定义。
- 用户只给几句话时也可以工作：自行形成合理的第一版假设和需要确认的关键决策；只在问题真的阻塞且无法安全假设时询问，优先一次一个重要问题，不发大表单。
- 用户已有完整产品定义时，不要求重跑发现阶段；转 `product-ia-interaction`。

## 工作步骤

1. **澄清价值与场景**：谁在什么情境下有哪项真实任务、目前如何做、为什么需要新产品；确认主要设备/平台、使用频率和熟练程度。目标用户可以是本人，不必虚构市场 persona。
2. **构造真实对象与行为**：列项目/记录/工作区/任务等核心领域对象的身份、关系、创建/编辑/归档/恢复生命周期；哪些信息用户拥有、哪些来自外部系统、哪些是估计或暂不可得。
3. **组织功能**：对每个用户提出的功能说明输入、可见结果、依赖、异常和用户收益；找出完成主任务必须具备却没说到的基础动作（创建、定位、修改、撤销、恢复、通知、权限、导出等因场景而定），不要机械加齐。
4. **范围与优先级**：必须做、下一阶段、明确不做、开放决策；把依赖复杂度与体验价值分开判断。用户提及的特殊交互、偏好与禁忌需显式保留。
5. **按不确定性选择方法**：遇到任务动机不清、跨角色协作、风险较高或外部依赖时，有针对性使用任务分析、JTBD、轻量竞品研究、Story Mapping、权限/服务链核查；参见 [可选专业方法](references/conditional-product-methods.md)。不要求每个个人项目依次运行完整 PM 仪式。再从代码、API、数据/平台限制验证关键前提；外部事实标注来源，不凭推测许诺拿不到的数据/权限。
6. **形成下一步输入**：核心用户任务、对象及关键状态、功能/约束、非目标、未决假设、建议的设计优先序。对尚未确认的关键设计点给出方案与理由，而非直接交给 coding agent 决定。

## 结果怎么交付

- 小问题：短结论 + 关键缺口，不自动生成长 PRD。
- 新产品完整设计：用 [产品定义骨架](assets/product-definition.md) 的相关部分。每项关键能力写到用户动作和产生的结果，能被后续 IA 设计引用。引用现有 canonical 文档时优先补写或修订原文，不再造平行权威。
- 输出应清楚区分 `confirmed`、`proposed`、`unknown`。给用户的待确认决策聚焦少数真正影响产品形态的事项；其他细节可提出默认建议，后续再改。
- **停止点**：核心任务、主要对象、必要能力、边界和明显假设足够清楚，便可移交 `product-ia-interaction`，不要求先完成所有商业调研、视觉和技术细节。
