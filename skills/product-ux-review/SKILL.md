# 产品与 UX 方案复审

## 审查对象

针对已给出的产品/前端方案或真实运行体验，判断它是否可以支撑**完整用户任务**，而不只是“功能列表已经有了”。可审查全产品或某一页面/流程。不要把未确定的产品方向交给 coding agent 作决定，也不要拿风格偏好替代产品问题。

## 过程

1. **确定本轮审查层级**：目标是产品完整性、IA、页面详设、行为细节还是已开发 UI；读取对应权威来源及用户已否定事项。不要以旧截图代替当前产品决策。
2. **按用户任务试走**：从用户第一次进入、主要任务、不同对象切换、完成、错误、撤销/恢复走到结束。判断信息是否在需要时出现，模块和动作是否能被找到、理解与执行。
3. **检查纵深而非多寡**：整体 IA→逐页空间层级→组件与按钮→反馈与状态→长文本、键盘、窄屏；不能只列五六条宏观设计建议。用 [详细审查视角](references/product-ux-completeness.md) 做针对性核对。
4. **区别三种问题**：产品/交互决策错误、视觉呈现造成的问题、与规格不一致的实现问题。后一类先查文档与实际代码，不能通过随意调整视觉来修复产品定义。
5. **分级与提出可实施改法**：每个重要问题写清用户遇到的情境、为什么有影响、具体如何改、是否需要用户决定；同时说明哪些建议不采纳及原因。把“可以改善”的偏好与真实阻塞分开。
6. **明确停止**：重要任务连续、状态真实、明显遗漏已解决即可收口；剩余轻微审美或低概率情况可记录，不反复寻找新问题。一次局部修改后重新检查受影响的整体流程，防止前后矛盾。

## 输出

优先给出**清楚的改动建议和可见表现**，而不是底层代码术语或笼统“提升体验”。小任务只给最少必要问题和改法；整项目复审可列优先级、问题出处、已决定/待决定事项。若用户只是问“是否可以收口”，没有实质障碍应回答可以，不捏造待办。

仅在需要完成新 IA 或详设时交给 `product-ia-interaction`；视觉错误交给视觉系统或 QA；实现偏差交给 `personal-ui-delivery`。不重复跑完整设计流程。

**验收**：没有影响核心使用的明显产品/交互空洞；关键小动作、状态、恢复和信息密度均已有具体处理；尚未实现或无法验证的事项被准确标注。
