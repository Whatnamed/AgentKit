# Spec & Diff Review

## 职责

独立核对**做的是否是原来要做的**（Spec）和**是否正确、简洁、符合项目工程约束**（Standards / Risks）。两条结论分开写，避免“测试全绿”掩盖漏功能，也避免“代码风格不喜欢”被误报成阻塞缺陷。

适用：已完成的功能、修复、候选分支或阶段合并前的审核；也可针对工作树尚未提交的改动。**不要**因为用户仅咨询一行代码，就自动运行全仓审计。不与 `product-ux-review` / `visual-qa` 重复：本 Skill 针对**代码变更与实现合同**，不是重新定义产品形态或主观视觉设计。

## 审查过程

1. **锁定范围和对照点**：确定用户指定的变更范围、基线提交/目标分支/PR；检查 Git 状态、commit 列表、已跟踪与未跟踪改动、实际 diff。三点 diff 与工作树未提交改动不是同一个集合；不猜“全部改动已提交”。默认不切换用户分支、不清理工作树。
2. **确认目标来源**：优先查用户指定的执行文档/Issue/原始产品、架构或 UX 规范，再结合实际项目 `AGENTS.md`、既定禁区和当前实现。区分用户确认的目标、执行者自行添加的方案及已实现事实。没有规格时只审能证实的风险，并说明 Spec 轴覆盖不足；不要发明一份用户未批准的标准。
3. **Spec 轴**：逐条关注缺失/部分完成的用户可见行为、边界与失败状态、API/数据契约、未授权的页面与范围变化、原任务的不变量、重要测试和真实交付证据。把“没有做”与“证据不足”分开。
4. **Standards / Risks 轴**：结合本仓规范与改动特征检查逻辑缺陷、真实输入/信任边界、并发及数据风险、错误处理、兼容性、依赖与安全、维护性及新抽象合理性。**主动留意无需求依据的签名、哈希、快照、备份、回滚层、额外状态、配置、重复测试与文档体系**；但项目真实业务、安全与恢复需求仍然优先。详见 [证据与适度审查](references/review-scope-and-evidence.md)。
5. **按风险验证，不按仪式验证**：优先已有检查结果和已运行的针对性测试。只有会改变结论、且有对应风险时才追加测试/真实 UI/接口验证；不要为了“充分证明”重复跑全套检查，禁止用新测试替代原任务未完成的问题。静态审查无法证明运行时表现时明确标未验证。
6. **形成有根据的结论**：每项问题给出位置（文件/行或变更点）、对应规格/规则/真实症状、为何会造成后果、严重程度及**最小合理修正**。区分阻塞、值得修复、可选建议；只要缺证据就不把“可能”写成确定 bug。
7. **收口**：按当前范围输出两个独立判断及余下风险。无需重新审查全部代码。未发现有影响的问题时直接给出“未发现阻塞”，不要为了输出内容而捏造改进点。

## 默认边界

- **只读审查**：除用户明确要求修复外，不修改代码、规范、测试、Issue，不自动提交、切分支或推送。即使是修复请求，也先限于有证据的问题，不展开无关重构。
- 单次审查不强制多 Agent、多模型、评分表或第二轮审查；可在高风险、多领域冲突且工具/权限支持时考虑独立视角。
- **验证强度与风险匹配**：局部样式、小修复可用局部检查；跨领域数据、权限、状态机、持久化和发布流程则需要真实相关回归。不以“节省 token”为理由省略必要验证，也不因“稳妥”无限堆测试。
- 对确实无法从代码、规格或运行事实判断的地方说明限制，不要编造 PASS 或申请无止境的补充证据。

## 输出

优先紧凑列出真正有影响的问题，再分别总结：

- `Spec`：完整 / 部分 / 不符 / 证据不足；具体缺口；
- `Standards & Risks`：存在阻塞 / 非阻塞改进 / 未发现重要问题；必要证据；
- `Verification`：哪些检查真正执行、哪些复用现有结果、哪些无法核对；
- `Decision`：可以继续合并/需要有界修复/用户必须决定。

这是用户的**实际工程审查能力**，不需要为了执行它创建新的 PRD、审计数据库或额外工作流。
