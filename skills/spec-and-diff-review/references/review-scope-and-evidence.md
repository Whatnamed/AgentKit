# 双轴审查：范围、风险与反过度工程化

**按需读取**。主要适用于大 diff、开发后重复审查、出现额外测试/恢复机制时。资料来源：[Matt Pocock code-review](https://github.com/mattpocock/skills/blob/49dd158d1076134a641b33efb035946536778336/skills/engineering/code-review/SKILL.md)、[Every ce-code-review](https://github.com/EveryInc/compound-engineering-plugin/blob/7a68002fc24139fe4876c759c9e5a3ebff976ad4/skills/ce-code-review/SKILL.md)、[Karpathy-inspired guidelines](https://github.com/multica-ai/andrej-karpathy-skills/blob/main/skills/karpathy-guidelines/SKILL.md)。吸收方法，不照搬原仓的框架、强制并行/审批。

## 范围先于判断

- 用户给 commit/PR 时按指定基线；没有时根据仓库分支与任务记录合理定位，并说清使用的基线。不要默认“main 总是对的”。
- 区分 `git diff BASE...HEAD`（相对 merge-base）、`git diff`（未暂存）、`git diff --cached`（已暂存），还应关注未跟踪文件与依赖/迁移/生成资产。
- 无规格来源：Spec 轴只说明可证实的目标与缺失依据；不能凭审查者“更合理”的产品方案重写要求。

## 重要审查类别（按变化内容选择）

| 维度 | 应找的证据 | 常见误判 |
| --- | --- | --- |
| 需求符合性 | 任务原文、设计决定、实际路径、变更点 | 测试绿了便默认做全；把建议当已确认要求 |
| 真实数据与状态 | 数据源、主流程、失败/恢复、权限与持久化 | 把 Unknown 当 Empty，把编排记录当真实进程 |
| 安全与边界 | 真实不可信输入、权限边界、不可逆操作、隐私 | “所有输入都加一遍 guard” 就是安全性提高 |
| 结构与维护 | 项目已有约定、局部性、必要抽象/依赖 | 任何重复代码都立即提炼通用框架 |
| 新增复杂度 | 新文件/层/测试/备份/迁移的独立需求 | Agent 自己先添加防御功能，再用它的存在证明必须保留 |
| 回归证据 | 最接近改动的测试/手工路径/日志 | 反复跑无关全套测试、跑了 build 就叫视觉验收 |

## 发现防御性膨胀时具体问

- 它保护的是**项目明确支持的现实输入/失败路径**，还是不可能的假设？
- 当前代码或外部系统已有校验、事务、版本控制/恢复机制吗？是不是重复实现？
- 新增的保障是否带来新的状态、Schema、迁移、测试、文档和未来维护负担？有独立需求覆盖这些成本吗？
- 若移除这层，真实用户需求/安全边界/数据完整性会怎样受影响？
- 它是用户批准的稳健性要求，还是 Agent 自行提出的“可选进一步强化”？

判定要由实际风险支持。保护支付、权限、隐私和数据完整性的关键防线不能因为“简洁”被删掉；无独立需求的恢复工厂、重复快照、自动生成审计文件也不能因为已经写出来就自动获得权威。

**停止条件**：重要风险都已有结论，能够决定接受还是局部修正；没有影响的主观代码风格、1px 差异或额外“或许可以更稳”的建议不制造新阶段。
