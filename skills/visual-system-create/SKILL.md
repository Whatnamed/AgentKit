# 新产品视觉方向与设计系统创建

## 目标

从一个已经有产品任务、页面职责和关键交互的项目出发，**创造一套属于它自己的视觉语言及可交付的设计系统**。不仅是几个颜色、字体和样式变量，而是从整体气质、页面区域层次、文字角色、留白/间距节奏，到组件各种状态、Light/Dark、对齐和真实宿主渲染的一致体系。

这是**可以反复比较和调整**的设计工作，不要求一开始就拍板每个 Token，也不在每次改观感时推倒已定的产品 IA。

## 分阶段设计（可从任意已有阶段继续）

1. **读产品 UX 约束**：先看页面/流程/数据与已有产品布局的权威决定，检查目标平台、内容密度、可访问性、语言与品牌限制。没有用户任务就不要先做一套空洞视觉；产品框架没定时标记为探索稿。
2. **定视觉方向而非随机拼样式**：根据产品气质和使用时长、可信程度、信息复杂度提出通常 2—3 个**真正不同**且适用的方向，必要时分析用户指定的品牌/参考图；对照文字、颜色和布局节奏说明差异，不照搬别人商标或业务模块。用户已明确风格则直接深化，不强行再做三套。
3. **在真实代表页面做小规模样张**：先覆盖最能暴露视觉问题的一页（高密度、长文本、交互复杂、侧栏/弹层多），同时准备若干真实状态。若只有静态稿，准确标记为 concept；不能从渲染图推断实际字体/交互已经正确。
4. **逐层定义设计规则**：主题及语义颜色、字体来源与中英文/Mono 角色、字号字重行高字距、Page/Section/Group/Item/Metadata 的空间层级和节奏、Grid/密度、背景/表面/分隔、图标与光学对齐、控件几何、动效/可访问性、Light/Dark、响应式和各状态。使用 [视觉决策层级](references/visual-decisions-and-iteration.md) 检查遗漏；当用户难以描述视觉问题或需要整套专业设计词汇时，读取 [视觉语言与诊断词汇](references/visual-language-and-diagnosis.md)，先解释“为什么这样看着不对”，再定设计动作。不要把源产品具体像素值当通用标准。
5. **一轮一轮收敛**：用户反馈“太疏”“行高偏大”“选中背景抢眼”“两个区域没有层次”等时，先查规范与实际样张，再找到最可能的因果变量，用最小联动修改一组有关系的 Token/组件；记录被否决、暂存和当前采用的方向。不要为了匹配局部视觉而随意调整已定内容结构、字重、行高、控件高和 margin 的所有变量。
6. **将选定系统落为单一权威**：明确 design intent、Token 语义与数值、组件族和 Props/Variants、文字/空间/状态样例、平台依赖、原型与源码映射、例外和没有设计到的范围。可按需用 [视觉系统规格骨架](assets/visual-system-spec.md)。持续改动时同步代码与规格，禁止两个 Token 权威源漂移。
7. **真实审查与停点**：可运行后检查长中文/英文混排、真实字体加载、最复杂页面、控件 hover/selected/focus/disabled/busy、对齐和 Light/Dark；清楚区分“方向已选”“系统已写”“代码实现”“人工验收”。没有重大明显不一致便结束当前视觉迭代，不无限搜细节。

## 输出与行动尺度

- 只有方向探索时：给出简洁可比较的选项、具体气质差异和推荐，不编造已验收 Token。
- 已选方向时：形成能被下一 Agent 使用的**可实现视觉系统**，包含完整文字/空间/组件状态与几页最关键的视觉适配，不能停在 moodboard。
- 用户修改局部外观时：给具体的观察、该改哪里、对其他页面的影响，按现有设计系统做增量迭代。
- 设计系统可以先 `draft` 再 `selected`、`implemented`、`validated`；后阶段不自动覆盖前阶段事实。创作与运行验证不是同一个概念。

## 边界与后继

该 Skill 不负责新产品整体 IA、业务状态来源或后端事实。若需复用指定视觉源而非重新创作，用 `visual-system-adopt`；若提取已有系统，用 `visual-system-extract`；实现后视觉审查可用 `visual-qa`，实际 Coding Agent 通过 `personal-ui-delivery` 落地。
