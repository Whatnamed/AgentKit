# UI 视觉真实对照与收口

## 原则

用户要求检查一页就检查一页，要求全面设计验收才覆盖系统矩阵。先分清**产品结构问题、视觉规范缺项、代码实现偏离、环境渲染问题**。不因“可能还能更美观”而无限制造修改任务。

## 核对流程

1. **定位真实权威**：已确认的产品 IA/UX、目标设计系统及其来源版本、当前代码与宿主、已采纳的视觉例外。不要拿旧截图当新版本规则，也不因为源项目的 PASS 就认为目标项目通过。
2. **获取真实呈现**：可访问应用时在真实目标宿主检查；最有辨别力的页面和状态优先。若只能读 CSS/代码或静态截图，应说明证据等级；构建/类型检查不能替代视觉验收。
3. **自上而下观察**：页面 shell、主次区域、Section/Group/Item/Metadata 的节奏、信息密度、滚动/折叠、空间比例、表面层级，再检查 Typography（真实字体加载、字重、行高、baseline、CJK/Latin/Mono）、控件几何、图标光学对齐、border/阴影、语义色与 hover/selected/focus。
4. **覆盖必要状态**：正常、空、错误/未知、Loading、长文本、高密度、Light/Dark、窗口尺寸/DPI/混排、Popover/Modal/表单/菜单及键盘操作，仅在产品实际支持和问题相关时展开。使用 [视觉检查参考](references/visual-observation.md)。
5. **先给根因，再修最少的变量**：判断是设计规则本身需要改、代码偏离、组件例外、字体/平台 fallback，还是业务状态和页面结构不合理；不混着同时乱改字体、间距、字重、控件高。
6. **带影响分级反馈**：写明问题场景、可见症状、用户影响、预期效果、证据/复现、建议修复与相关页回归；同一个根因可合并，不重复列二十条描述同一件事。
7. **确认收口**：影响关键任务或明显一致性的缺陷处理后回看**本轮总体变化**，检查文档与代码同步、关联页面不回归。少量主观差异/极低影响问题可记录并停止；缺真实数据或 Windows 宿主时标记 `deferred`，不谎称通过，也不无止境重复尝试。

## 交付

小审查给短而可执行的结论；复杂验收给问题-证据-改法-状态表。按 `pass / justified-exception / needs-fix / deferred` 记录，而非一律“重做”。已无需改变且证据足够时要明确说明可以结束。

若发现实际功能/IA 问题，交还 `product-ia-interaction` 或 `product-ux-review`；只修改代码与同步文档可交由 `personal-ui-delivery`。
