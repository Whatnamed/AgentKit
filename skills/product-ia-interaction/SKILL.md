# 产品 IA 与交互设计

## 适用范围

以当前产品目标和用户任务为起点，产出**页面为什么存在、承载什么任务、用户怎样在状态间行动**的可实现方案。可用于新应用的 IA、已有页面重构或单个用户流程。不要因用户问一个局部交互，就重新设计整个产品。

如目标、用户和产品边界本身仍未成形，先指出关键未知；能局部推进就只推进有依据的部分。不要为了填满模板假设业务事实。

## 执行

1. **确认权威与任务范围**：整理用户明确决定、当前目标规格、运行中事实、旧设计与待确认假设。分别写出“目标应如何”和“目前实际上如何”；二者冲突不得暗中以现状覆盖目标，也不得把旧文档当最新代码。只有必要时读取 [证据与状态检查](references/evidence-and-state.md)。
2. **从用户任务建立对象与关系**：列核心对象、关键身份、生命周期、相关权限/来源、不可跨越的业务边界；仅在会影响 UI 时展开技术对象。指出用户如何找到对象、完成任务、验证结果。
3. **按认知任务分配页面职责**：决定一级目的地、页面/区域角色、导航路径、信息密度和主次层级。每个区域要回答清楚的用户问题；同一组件风格不要求同一业务布局。没有独立任务就不要新增页面。
4. **逐条走核心交互路径**：起点、触发、反馈、下一步、返回或取消；跨页上下文的保留/重置；选择与展开是否独立；编辑、保存、失败、恢复、长内容、空白/未知、狭窄视窗与键盘路径。
5. **验证状态语义**：分清未开始/进行中/完成/失败/未知/无数据等实际业务差异，检查计算分母、时间和来源；不把“尚不能判断”渲染为“通过”，不制造不可用操作。按任务可用 [状态检查参考](references/evidence-and-state.md)。
6. **审视取舍并定停点**：以关键任务完整、事实正确、可理解、可恢复为优先级；反对只因“更丰富”而增加 KPI、卡片、说明文案或页面。记录采用、否决、延期原因及有证据的例外。

## 交付尺度

- 简单问题：直接回答必要调整与原因，不自动生成 PRD。
- 跨页面/完整 IA：给出页面职责表、1–3 条关键任务路径、各关键状态/操作、跨页上下文及待决定项。需要落盘时可使用 [IA 合同模板](assets/ia-contract.md)，删除所有不适用章节。
- 若有既存规范，优先对其做定点修订与差异说明，不平行再造第二份权威文档。
- 对不可证实内容标注 `assumption`、`unresolved` 或 `needs runtime verification`，不伪造用户确认。

## 排除与交接

不负责选择品牌字体/Token/主题，不以视觉参考替代 IA，不实现 UI，不执行全套测试。已确定产品与页面职责后，可交给视觉系统设计或实现；已有完整 IA 而只需外观迁移时，不触发本 Skill 重做业务布局。

完成条件：主要用户任务有明确入口、动作、反馈、状态及返回路径；剩余未知有归属；方案可供下一阶段执行，不要求无限 polish。
